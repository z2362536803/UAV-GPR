## 0. 第一个 Issue 之前

当前项目初始化内容和本 Issue 计划需要先由项目负责人审查，并作为**初始基线提交**进入 `main`。在此之前不要启动 ISSUE-001，否则执行器会把整套未跟踪初始化文件误认为自己的改动，也无法可靠创建/比较独立分支。初始提交、远端和分支策略由项目负责人明确授权执行，不由 Harness 自行决定。

## 1. 使用方法

1. 先确认目标 Issue 的所有依赖已通过验收，并读取对应里程碑文件。
2. 为该 Issue 使用独立分支/工作树；当前 `main` 不直接开发。
3. 将该 Issue 下的“DeepSeek Harness 提示词”原样交给执行器。
4. 人工审查范围、测试证据、数据语义和参考来源后再把 Issue 标记为完成。
5. 发现设计冲突时暂停 Issue，先更新计划或新增 ADR；不得让临时代码偷偷改写架构。

## 2. 状态定义

- `Planned`：已规划，依赖或实施尚未开始。
- `Ready`：依赖已完成，验收口径仍适用，可以开工。
- `In progress`：仅一个执行者正在处理。
- `Blocked`：有明确外部条件或设计决策缺失。
- `Review`：实现和测试完成，等待人工审查。
- `Done`：验收标准和完成定义全部满足。

本文件初始不伪造进度；所有 Issue 均为 `Planned`。

## 3. DeepSeek Harness 通用执行协议

每段 Issue 提示词都会要求执行器遵守以下协议：

1. 工作目录固定为 `E:\wurenjiruanjian`。完整阅读 `AGENTS.md`、本文件、目标 Issue 和它列出的专题文档。
2. 先检查 `git status`、依赖 Issue 的实际代码/测试证据和现有用户修改。依赖缺失或工作树冲突时停止并报告，不假装完成。
3. 只实现目标 Issue；不顺手实现后续 Issue，不重构范围外模块，不修改两个参考项目。
4. 先写/更新能够失败的测试，再写最小实现。硬件路径必须有模拟器或协议夹具；没有硬件时不得伪造真机通过。
5. 严格遵守不可变 raw、多通道 shape、真实时间/GNSS、store-then-forward、UI 线程和 fail-closed 规则。
6. 迁移参考代码前记录 branch、HEAD、worktree status、实际源文件 SHA256、迁移/排除内容和黄金样本来源。
7. 只使用项目允许的依赖。新增依赖、schema、协议或跨层引用前说明必要性；架构决定缺失时先写 Proposed ADR 并等待批准，而不是扩大 Issue。
8. 运行目标测试、相关回归、全部非硬件测试、Ruff 和 mypy。测试失败不得删除测试、降低断言、吞异常或扩大 `sleep`。
9. 检查 diff、状态、缓存和生成物；不得提交实测数据、密钥、日志、地图缓存或参考仓库文件。
10. 默认不 commit、不 push；只有 Harness 调用者明确授权时才进行。禁止强推和破坏性重置。
11. 最终报告固定包含：实际改动、测试命令与结果、验收逐项对应、未完成/风险、工作树状态。随后停止，不执行下一 Issue。

## 6. 并行规则

只有依赖已完成且不同时修改同一核心契约时才并行。例如：完成 003/004/005 后，007 与部分 015 可并行；完成 024 后 GNSS reader 与处理算法不应共享文件。schema、协议、主窗口骨架和应用状态机属于高冲突区域，默认串行。

执行器不得根据“看起来独立”自行并行或跳过门禁。发现依赖表需要调整时先修改本计划并说明原因。
