# Issue 独立审查标准

版本：1.0
状态：项目合并前质量门禁

## 1. 目的与适用范围

本标准用于独立验证一个或多个 Issue 的完成报告是否真实、完整并符合项目规范，以及对应代码是否可以进入目标主分支。

审查者只需要获得执行者完成报告和当前仓库访问权限。执行者或报告提交者不需要重复填写 Issue、分支、基线、提交、文件或测试参数；审查者必须从完成报告、Git、项目文档和代码中自动识别并交叉验证。

本标准适用于功能、修复、文档、工具、测试、重构、数据格式、协议、UI、设备和发布验收 Issue。多个 Issue 批量交付时，每个 Issue 仍须独立验收。

## 2. 审查者权限边界

审查者不是本轮执行者。除非项目负责人明确授权，审查期间不得：

- 修改、格式化或重写项目文件；
- 自动修复缺陷；
- 创建提交、合并、推送或改写 Git 历史；
- 删除、移动或清理工作区文件；
- 修改参考项目或实测数据。

允许执行只读检查，以及不会修改项目内容的测试、静态分析、导入、启动和合成故障验证。测试产生的已忽略缓存不得进入提交，审查结束时必须复查工作区。

## 3. 证据权威顺序

发生冲突时按以下顺序认定事实：

1. 当前任务明确验收条件；
2. 根目录 `AGENTS.md`；
3. 已接受 ADR；
4. Issue、里程碑和专题设计文档；
5. 当前仓库代码和自动化测试；
6. Git 历史、差异、reflog 和工作区状态；
7. 执行者完成报告。

完成报告是待核验声明，不能替代代码、Git 或测试证据。报告与仓库冲突时，以仓库证据为准并单独列出差异。

## 4. 自动识别审查范围

审查开始时必须从完成报告提取：

- Issue 编号、标题、依赖和声称状态；
- 开发分支、目标分支、基线和提交哈希；
- 修改文件、已完成项、未完成项和已知限制；
- 测试命令、结果、硬件条件和风险；
- commit、push、merge、PR 或历史重建说明。

随后检查仓库根目录、当前分支、工作区、本地与远程分支、共同祖先、提交父子关系、reflog、基线后完整差异、未提交修改和未跟踪文件。

范围按以下顺序确定：

1. 报告明确列出的 Issue、分支和提交；
2. Issue 文档、里程碑和提交信息能相互印证的范围；
3. 当前分支相对目标主分支共同祖先后的提交；
4. 已进入主分支时，结合提交时间、信息和文件差异识别；
5. 报告与 Git 冲突时采用 Git 事实。

不得只凭分支名确定范围。若无法唯一确定基线或 Issue，继续完成可验证检查，列明不确定内容和影响，最终结论必须为 `BLOCKED`。

## 5. 必读资料

代码审查前必须完整阅读：

- `AGENTS.md`、`CONTRIBUTING.md`、根 README 和 `docs/INDEX.md`；
- `docs/issues/README.md`、目标 Issue 详细文档及所属里程碑；
- 修改模块对应的架构、数据、协议、设备、UI、性能和测试文档；
- 相关 ADR、参考迁移规则和当前目录内其他 `AGENTS.md`；
- 完成报告引用的计划、报告、样本或外部基线。

每个 Issue 必须分别提取目标、范围、排除项、依赖、实施要求、验收标准、测试要求和交付要求。不能用“整批可以运行”代替逐 Issue 验收。

## 6. Git 与交付审查

必须检查并报告：

- 当前分支、目标分支、共同祖先和审查基线；
- 本批提交及其父子关系、作者、时间和对应 Issue；
- 一个提交是否不合理混入多个 Issue；
- 一个 Issue 是否被拆成无法独立理解的碎片；
- 是否存在范围外修改、遗漏提交、未提交或未跟踪文件；
- 是否提交缓存、日志、构建物、密钥、本地配置、实测数据或参考仓库文件；
- 是否改变公共数据、schema、协议或架构契约且缺少文档/版本/ADR；
- reflog 是否显示 reset、rebase、amend 或重建历史；
- 是否存在强推、绕过主分支保护或报告哈希不一致的迹象；
- 多 Issue 的依赖顺序及可否安全拆分合并。

只能报告证据能够证明的 Git 操作。例如 reflog 只显示 `reset` 时，不得擅自断言使用了 `reset --hard`。

## 7. 逐 Issue 验收矩阵

每项验收标准只能使用以下状态：

- `PASS`：代码与测试证据明确证明满足；
- `FAIL`：实现缺失、错误或违反要求；
- `PARTIAL`：只完成部分或只覆盖正常路径；
- `BLOCKED`：因关键环境、硬件或信息缺失无法验证；
- `NOT APPLICABLE`：核对后确认不适用。

矩阵每一行必须包括：验收标准、状态、精确代码证据、实际测试证据、问题或限制。代码证据应尽量精确到文件和行号。

依赖 Issue 必须检查实际代码和接口兼容性，不能只引用执行者声明。

## 8. 代码审查维度

根据实际修改范围，至少检查以下内容：

### 8.1 正确性与状态

- 正常、错误、取消、恢复和边界路径；
- 状态转换、默认值、异常传播和静默失败；
- 索引、长度、单位、时区、单调时钟和数据关联；
- 重复、乱序、竞态、丢失和错误成功状态。

### 8.2 架构与依赖

- 包依赖方向和 core 隔离；
- 地面端主应用与空中端轻量执行器职责；
- UI、application、设备、算法、存储和 transport 边界；
- 阻塞 I/O 和长计算是否越过线程边界；
- 是否破坏后续 Issue 的扩展点。

### 8.3 数据与兼容性

- raw 不可变、多通道 shape、轴、单位和 dtype；
- ID、UTC、单调时钟、GNSS、质量和 hash 契约；
- schema/协议版本、未知版本、旧数据和损坏数据；
- 写入原子性、恢复、幂等、冲突 fail-closed 和空地对账；
- JSON、HDF5 或二进制序列化是否拒绝非有限或不支持值。

### 8.4 设备、GNSS、处理、传输与 UI

- 设备接口是否可模拟，超时、断开、重连和取消是否定义；
- GNSS 是否按 sweep 中点匹配，MSL/AGL 是否分离，stale/no-fix 是否显式；
- 校准/处理是否分阶段、数值稳定且不覆盖 raw；
- 传输是否处理消息边界、重复、乱序、ACK、背压和重启恢复；
- UI 是否非阻塞、状态可见、布局符合地面/空中职责并支持离线地图降级。

### 8.5 安全与可维护性

- 敏感信息、机器路径、危险文件操作和日志泄露；
- 配置默认值、依赖声明、类型、命名和模块职责；
- 重复实现、隐藏临时代码、性能退化和无界资源。

## 9. 测试与复核

先记录执行者声称运行的测试，再使用项目规定命令复跑。至少考虑：

- 目标 Issue 定向测试；
- 全量非硬件测试；
- Ruff、mypy、格式和 diff 检查；
- 包导入、应用启动或 Qt offscreen smoke；
- 数据/协议往返、故障注入和异常路径；
- 必要的合成契约探针；
- 工作区测试后清洁状态。

测试必须记录实际命令、解释器版本、退出码、通过/跳过/失败数量和失败原因。硬件、专用网络或外部服务缺失时不得伪造通过；应使用模拟器、夹具或回放，并明确真实硬件是否仍阻止合并。

标准门禁全绿不等于验收自动通过。审查者必须补查执行者测试未覆盖、但需求明确要求的反例。

## 10. 完成报告真实性核对

逐项核对：

- 功能、文件、提交、分支和哈希是否真实；
- 声称未修改的范围是否确实未改；
- 测试数字和命令能否复现；
- 已知限制和风险是否完整；
- 是否隐藏失败、跳过、占位、未提交修改或范围偏离；
- 是否把模拟结果、字段存在或正常往返误报为完整契约达成；
- 时间、manifest、黄金样本和参考源哈希是否与最终提交一致。

所有不一致单独列入“报告与事实差异”。无法事后证明的过程声明应标为“未发现反证”或“无法独立验证”，不得直接写成已证实。

## 11. 问题等级

- `P0`：严重数据破坏、安全事故或系统完全不可用；
- `P1`：阻止合并的功能、数据、架构、可靠性或关键验收缺陷；
- `P2`：应修复的重要缺陷，影响范围相对有限；
- `P3`：低风险文档、可维护性或改进项。

每个问题必须包含：等级、标题、所属 Issue、文件与行号、触发条件、实际影响、违反的要求和最小修复方向。不得为显得严格而虚构问题。

## 12. 最终结论规则

最终结论只能是：

- `PASS`：所有 Issue 验收均满足，无阻止合并问题；
- `PASS WITH CONDITIONS`：主要目标完成，只剩明确、低风险且不阻止本次合并的条件；
- `FAIL`：存在未完成验收、错误实现或阻止合并问题；
- `BLOCKED`：范围无法可靠确定或关键环境缺失，无法形成结论。

任一 Issue 存在 `P0`、`P1`、关键验收失败或必要测试失败时，整批不得判定为 `PASS`。多个 Issue 中任一项不合格，必须同时给出整批结论、每个 Issue 结论、可否拆分合并及依赖影响。

## 13. 固定输出格式

审查报告必须按以下顺序输出：

1. 审查结论；
2. 自动识别的审查范围；
3. 主要问题，按 P0 到 P3 排序；
4. 逐 Issue 验收矩阵；
5. Git 与交付检查；
6. 测试与验证结果；
7. 报告与事实差异；
8. 剩余风险；
9. 合并建议；
10. 最小修复清单。

审查结束后立即停止，不修改代码，等待项目负责人决定修复、拆分或合并。

## 14. 修复后复审

修复提示词必须只包含阻止合并和明确要求处理的最小问题，不顺手实现后续 Issue。修复执行者应：

1. 从审查结论提取对应 Issue、文件、失败契约和测试；
2. 先增加能够复现问题的失败测试；
3. 实现最小修复并保留既有公共语义；
4. 运行定向测试、全量非硬件门禁、静态检查和 diff 检查；
5. 检查工作区和提交边界；
6. 报告每项审查问题如何关闭，以及仍未关闭的限制；
7. 停止，不自动进入下一 Issue，不 merge 或 push。
